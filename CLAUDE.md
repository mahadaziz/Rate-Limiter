# Distributed Rate Limiter / API Gateway

## Overview
Build a distributed rate limiter in Python using FastAPI and Redis. This is a portfolio project meant to demonstrate distributed-systems reasoning: atomic operations under concurrency, multi-instance coordination through shared state, and graceful degradation on dependency failure.

## Stack
- Python, FastAPI
- Redis (via redis-py)
- Docker + docker-compose
- nginx or Caddy as load balancer

## Build Order

Work through these in order. Confirm each step actually works before moving to the next, especially step 2 before step 4. The atomicity logic needs to be verified correct on a single instance before adding distribution on top of it.

### 1. Scaffold
- FastAPI app + Redis, docker-compose.yml with both services
- Basic health check endpoint (`GET /health`) to confirm the stack runs end to end

### 2. Rate limiting core
- Implement a sliding-window-log rate limiter as a Redis Lua script, executed via `EVAL`
- The check-and-increment must be a single atomic operation, not separate `INCR`/`EXPIRE` calls
- Goal: no race condition where two concurrent requests both read "under limit" before either writes

### 3. Per-client config
- API-key-based client identification
- Two tiers (free, pro) with different request limits
- Store tier config in a simple in-memory dict for now (no DB needed yet)

### 4. Distributed setup
- docker-compose runs 3 instances of the FastAPI app, all connected to the same Redis instance
- nginx or Caddy in front as load balancer
- This step proves the design: without step 2's atomicity, the limit would get exceeded under concurrent cross-instance load

### 5. Fallback strategy
- If Redis is unreachable, fail open (allow requests through)
- Wrap Redis calls in try/except, log every fallback trigger
- Be able to articulate the fail-open vs fail-closed tradeoff

### 6. Metrics endpoint
- `GET /metrics` returns allowed/denied request counts per client
- Should make rate-limiting behavior visible without reading logs

### 7. Load test script
- asyncio + aiohttp, or locust
- Fire concurrent requests against the load balancer from multiple simulated clients
- Goal: prove the limit holds correctly across all 3 instances, no overcounting or undercounting under concurrency

### 8. Structure and docs
- Clean separation: FastAPI routes / Redis-Lua limiter logic / config
- README explaining the architecture and how to run locally with docker-compose

## Constraints
- Don't skip to distributed setup (step 4) before single-instance rate limiting (step 2) is confirmed correct
- Don't use plain `INCR`/`EXPIRE`, atomicity is the point of the project
- Keep tier config in-memory for now, don't add a database unless asked

## Commits
